# 基准与天花板：两类错误的成因与防线

> 2026-11-23 一天之内，这两类错误各犯了 3–4 次，且都导致**结论方向反转**。
> 本文不是规范宣讲，是把每次犯错的**机制**摊开，然后给出**能被机器拦住**的防线。
>
> 核心判断：**这两类错误的共同点不是"算错了"，是"同一个数在多处各写一遍"和"两个实现语义不同却放在一起比"。**
> 所以防线必须是结构性的——让错的数**无法进入比较**，而不是再加一句提醒。

---

## 一、两类错误的分野

| | 基准错 | 天花板错 |
|---|---|---|
| 问题 | 拿两件**不同的活**比 | 分母**不是这台机器的能力** |
| 今天实例 | ① 融合 vs 单算子 ② 1 份输出 vs 2 份 ③ aiter fp8 vs hipBLASLt bf16 | ① 1100 标称 ② 185 反推 ③ 540 无来源 ④ 310 单轮采样 ⑤ 1724 无标定 |
| 后果 | 「快 1.18×」实为慢 6.7% | 「还有 11 倍空间」实为「已到顶」 |
| 判据缺失 | 没有「语义等价」的声明 | 没有「分母可复跑」的强制 |

**两类错误的同一个根**：数字写在各处，没有一个**唯一可执行的真值源**。

实测证据（`grep` 结果）：
- 融合残差 RMSNorm 的字节数在 **6 处**各写一遍（`_common.py`×2、contract×2、card×2、candidates×1），**没有一处写对**（都以为写 1 份输出）
- `1724` 被硬编码在 `_common.py:186`、两个 contract、多张卡片、多个 case 里

## 二、基准错：语义对齐必须**机器可判**

### 今天的三个实例

| 实例 | 比较 | 为什么错 |
|---|---|---|
| `fused-add-rmsnorm` | 融合实现 vs 单算子 | 融合省一趟 HBM 是设计意图，拿它比单算子当然赢 |
| `rmsnorm-fused` | 我们（1 份输出）vs lightop（2 份） | 少干 1/3 的活 |
| `gemm-fp8` | aiter fp8 vs hipBLASLt bf16 | 跨库比，两库的 bf16 本身差 8.8× |

### 为什么「写文档提醒」不管用

`variants.yaml` 里其实早就写了「融合残差版本会原地改写输入」。
但它**只说了改写，没说输出几份**。而 `_common.py` 的 `VARIANTS` 元组里对每个变体
只有名字、没有语义。

**信息在，但不在机器能读的位置。**

### 防线：semantics 声明 + 对齐断言

每个变体必须声明它的**访存契约**（这是唯一能机检等价性的东西）：

```yaml
# variants.yaml
- name: fused-3pass-triton
  semantics:
    inputs:   [x, residual, weight]     # 读哪些
    outputs:  [out, residual_out]       # 写哪些（**关键：几份**）
    mutates:  []                        # 原地改写哪些
    traffic_passes: 4                   # 2 读 + 2 写
- name: lightop-fused
  semantics:
    inputs:   [x, residual, weight]
    outputs:  [out, residual_out]
    mutates:  [x, residual]
    traffic_passes: 4
```

**跨实现比较的前置断言**（机器执行，不是人工检查）：

```
assert a.semantics.outputs == b.semantics.outputs, "输出集不同，不可比"
assert a.semantics.inputs  == b.semantics.inputs,  "输入集不同，不可比"
assert a.semantics.traffic_passes == b.semantics.traffic_passes
```

不等则**拒绝出 ratio**，只允许出「两个各自相对自己的基线」。

这条比 E27 强：E27 只要求「写了对齐说明」，这里是**自动比对**，写错也过不去。

### 还要补一条：`run_isolated` 丢弃了附加输出

实测三个实现的返回：

```
ref-heavy            返回 Tensor (1 份)
fused-3pass-triton   返回 Tensor (1 份)   ← 我们最初就是这么写的
lightop-fused        返回 tuple(2 份)     ← run_isolated 只取了第 [0] 个
```

**`run_isolated` 只 clone 第一个输出，第 2 份被静默丢弃。**
这就是为什么「少写一份」没被任何检查发现——检查本身看不见第二份。

修法：`run_isolated` 必须保留并校验**全部**输出，数量与 `semantics.outputs` 对不上就报错。

## 三、天花板错：分母必须**可复跑**且**分口径**

### 今天五次实例的对照

| 声称 | 实测 | 偏差 | 根因 |
|---|---|---|---|
| 1100（标称） | 1724 | 低 36% | 拿型号名当能力 |
| 185（反推） | 279~310 | 低 34% | 用小形状（N=2048）反推 |
| 540（无来源） | 49.8（某实现） | **高 10.9×** | 来源是 kb 记录，无脚本 |
| 310（单轮采样） | 279 | 高 11% | 偶发高值当峰值 |
| 1724（无标定） | 实测最高 1634 | 高 5.5% | 只有断言，无测量 |

### 为什么「三层口径」（E23/E24）不够

已经分了 `nominal / achievable / impl_measured`，也加了 E23 要求标注。
但仍有问题：

1. **标注是自由的**——可以写 `achievable` 但那个数根本没有测量记录
2. **同一张卡两个分母**（0.63@1724 与 0.73@1498）让人不知道用哪个
3. **峰值常数仍在多处硬编码**

### 防线三条

**① 分母只能来自 `constants.yaml`，且有 `reproduce` 才能用**

```
任何达成率的分母 → 必须能解析到 constants.yaml 的一个条目
                 → 该条目 status=measured 且有 reproduce 脚本
                 → 否则该 ratio 不许写进卡片，只能写「未测定」
```

这条 E25 已经在 `evidence` 上做了，但没管**分母**。要扩展到 `ratio.vs` 里引用的常数。

**② 双分母必须给出「用哪个」的规则，不能并列摆着**

今天的 `0.63(1724) / 0.73(1498)` 就是反面教材——读者不知道该信哪个。

规则：
```
报「离硬件上限多远」     → nominal
报「还有多少优化空间」   → achievable（本机最佳实现实测）
报「这条实现多快」       → impl_measured
```
**一张卡只报一个主数**，其余进 `scope.note`。

**③ 常数只许在一个地方定义，其他地方引用**

现在 `1724` 硬编码在 6+ 处。应改成：
```python
# 所有地方都从 constants.yaml 读，不在代码里写字面量
peak = roofline.constant("memory.stream_read_peak")
```
加一条测试：全仓扫描，`plugins/ops/**/*.py` 里不许出现裸的带宽/TFLOPS 字面量。

## 四、这两条防线怎么落地（最小改动）

| 防线 | 落地物 | 机检 | 工作量 |
|---|---|---|---|
| 语义对齐 | `variants.yaml` 增 `semantics` 块 | 比较前断言 inputs/outputs/passes 相等 | 半天 |
| 附加输出不丢 | `run_isolated` 保留全部输出 | 输出数 ≠ semantics.outputs 即报错 | 2h |
| 分母可复跑 | `ratio.vs` 引用的常数必须可解析到 constants.yaml 且带 reproduce | 新 E28 | 半天 |
| 单主数 | 卡片只允许一个主 ratio，双分母进 note | 已有 E24 扩展 | 2h |
| 常数不硬编码 | 全仓扫裸字面量 | 新测试 | 2h |

## 五、一条更根本的判断

今天所有错误里，**没有一次是「算法选错了」**。
全是**口径**：比错了对象、用错了分母、量错了遍数。

这说明这类系统的瓶颈不在「会不会优化」，而在**「知不知道自己在优化什么」**。

所以防范的重点不该是「多写检查」，而是让**每个数字都带着它的来历**：
- 分母从哪来（constants.yaml 的哪条，status 是什么，哪个脚本能复跑）
- 分子怎么算的（几读几写，含不含分配）
- 跟谁比（对方的 inputs/outputs/passes 是什么）

**一个数字如果说不清这三件事，它就不该出现在结论里。**

这条不是新概念——`ratio.vs + scope` 就是这个意思。问题是它一直是**自由文本**，
所以能绕过。上面的防线本质是把这三件事从「散文」变成「必填字段 + 断言」。
