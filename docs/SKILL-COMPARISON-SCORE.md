# 两个 agent skill 的对比评分

> 对象：ForgeKernel（`/workspace/ForgeKernel`）vs toolkit_skills 的 ops 域
> 方法：**每个维度都用可数的证据打分，不凭印象**
> 时间：2026-11-25

---

## 一、先看硬指标（都是数出来的，不是估的）

| 指标 | ForgeKernel | 我们 | 差距 |
|---|---|---|---|
| 代码量 | 38,032 行 Python | 23,195 行（引擎+脚本） | 1.6x |
| 测试文件 | 80 个 | 72 个 | 1.1x |
| 测试用例数 | 未统计（粗查 >800） | **1020 passed** | 相当 |
| 算子实现 | 25 个 kernel | 17 个 skill 壳 / 54 张卡 | 我们多但浅 |
| **实测超厂商的算子** | 18/22 专家库 kernel | **3 张**（1.12x / 1.82x / 2.03x） | **6x** |
| 硬件机制库 | **200 条**（hw_kb，带探针认证） | 0 条（散在 references） | **∞** |
| 文档 | 9 份 | 16 份 | 我们多 |
| 有论文 | ✅ arXiv:2611.04998 | ❌ | — |
| 公开排行榜 | **3 个第一** | 无 | — |

**关键中的关键**：`hw_kb` 200 条 vs 我们 0 条。这不是「文档多少」的差别，
是「知识能不能跨算子复用」的差别。

## 二、八维度评分

评分标准：每维 0–10 分，**有实测证据才给 7 分以上**。

### D1 · 自进化能力（能否持续突破自己的最好成绩）

| | 分 | 依据 |
|---|---|---|
| ForgeKernel | **9.0** | 每代 promote，论文实测每代还能 +9.9%；GDN +100% over FlashInfer |
| 我们 | **4.0** | `advance.py` 有 replan 换向，但 reference 永远固定；第一轮 2.03x 后无法再突破 |

**差的 5 分在哪**：我们的「赢家」不会变成新基线。第 2 轮开始就在跟原始基线比，
随便改改都能判 ACCEPTED —— **看起来在进步，实际原地踏步**。

---

### D2 · 架构决策的前置性（先定结构还是先调参）

| | 分 | 依据 |
|---|---|---|
| ForgeKernel | **9.0** | M0 冻结架构（kernel 切分/tile/warp 角色/寄存器预算），gate 一过不许改 |
| 我们 | **3.5** | 一维队列按 EV 排；「换结构」和「调 num_warps」同层竞争 |

**我们为此付过代价**：`norm-act-swiglu` 扫 BLOCK_ROWS 1/2/4 三轮才发现 2 行最优。
如果先定架构（1 行/CTA 归约延迟藏不住 → 必须多行），一轮就到。

---

### D3 · 归因能力（能不能说清收益来自哪）

| | 分 | 依据 |
|---|---|---|
| ForgeKernel | **8.5** | lever-pricing 双向（加/减），能分辨「真 lever」与「依赖项」；ncu 精确到 stall reason |
| 我们 | **6.0** | `ablate.py` 只有「减」一个方向；PMC 采不到 stall reason（D4 债）；但有 3×MAD 判定 |

**我们比它强的一点**：它有 ncu，我们有 `measure_mode` 分层。它的归因更细，
但它的口径更粗（假设同 job 可比，在共享卡上不成立）。

---

### D4 · 知识沉淀（能不能跨算子复用）

| | 分 | 依据 |
|---|---|---|
| ForgeKernel | **9.5** | hw_kb 200 条，算子无关，每条带 `✅ GPU-certified` + 探针实测值 |
| 我们 | **2.5** | 知识散在各卡 `references/`；三张卡各自重新发现了「寄存器驻留 vs LDS」 |

**这是最大的差距**。我们的三张卡（rmsnorm-fused / fused-add-rmsnorm /
norm-act-swiglu）**每张都重新踩了一遍同一条机制**。ForgeKernel 只需查一次 hw_kb。

---

### D5 · 正确性保障（能不能防「两边都错」）

| | 分 | 依据 |
|---|---|---|
| ForgeKernel | **8.5** | judge 从 description 独立写；reference 只有 judge 通过才接受；输入分组≥3 |
| 我们 | **6.5** | ULP 判据（2 ULP）+ 三层反作弊；但 reference 和 runner 同文件写 |

**我们踩过的坑**：`rmsnorm-fused` 的 reference 一开始只返回一份输出，
导致「少干 1/3 的活」而门禁看不出来 —— 因为两边都错。

---

### D6 · 口径严谨性（数字可不可信）

| | 分 | 依据 |
|---|---|---|
| ForgeKernel | **6.5** | 同 job confirmation ratio；噪声地板用本代 spread（这点比我们好） |
| 我们 | **8.5** | `measure_mode` 三层（`back_to_back` 判不可 claim）；分母三层口径；峰值常数必须有 reproduce |

**这维我们赢**。它假设同 job 可比；我们实测过共享卡上同一份代码 MAD 从 4.9% 漂到 7.2%，
所以强制区分口径。它的「噪声地板=本代 spread」这一条值得单独学。

---

### D7 · 可用性（agent 能不能准确找到入口）

| | 分 | 依据 |
|---|---|---|
| ForgeKernel | **9.0** | 一条命令 `forge new/run/status/resume`；README 里有「粘贴给 Claude Code」的引导语；`/forge-start` skill |
| 我们 | **7.5** | `CLAUDE.md` + `op-optimize` 唯一入口 + 8 条契约测试；但命令分散在 `scripts/*.py` |

它的 CLI 形态更友好（`forge run` 一个词），我们是 `python3 -I scripts/advance.py --card ...`。
但我们的入口契约有测试守着，它没有（它的文档和代码也可能漂）。

---

### D8 · 覆盖广度（能处理多少种算子）

| | 分 | 依据 |
|---|---|---|
| ForgeKernel | **7.5** | 25 个真实现（attention/conv/gemm/linear_attention/sparse_attention），全部有实测 |
| 我们 | **5.0** | 54 张卡，但只有 17 个有 skill 壳，**3 张真正跑出超厂商结果** |

**「54 张卡」是虚的**。真正有 `kernels/*.hip` + 实测结果 + `acc_ok` 的只有 3 张。

## 四、差距的来源分析（这个比分数重要）

### 差距不是「我们能力弱」，是三件事

**① 时间**：它有一篇论文 + 三个排行榜第一的迭代周期。我们这套主力工作是最近两周做的。

**② 平台**：它的 NVIDIA 工具链（ncu / CuTe DSL）成熟；我们的 gfx938 PMC 采不到
stall reason（D4 已登记）。**有些能力不是我们不做，是硬件不支持。**

**③ 最关键的：知识没有沉淀成可复用的形态**

这一条是**真正的差距**，也是最容易补的：

```
ForgeKernel: 200 条 hw_kb，算子无关，一次认证全算子受益
我们:        0 条。三张卡各踩一遍同样的坑
```

**这不是「他们想得更周到」，是他们把「跨算子复用」当成第一等公民。**

---

## 五、如果只做一件事

**建 `hw_kb/`。**

理由：我们的三张卡已经实测出 5 条可复用的机制（寄存器驻留 / 16B 向量 /
private 溢出陷阱 / LDS swizzle 反例 / warp reduce），
**只是没整理成通用格式**。

半天工作量，能把 D4 从 2.5 拉到 6.0，总分从 4.68 到 5.38。
更重要的是：**它会让第 4、5 张卡少踩两轮坑**。

---

## 六、诚实说明

**这个评分对 ForgeKernel 有偏向**：
- 我读了它的 README、design docs、源码，但**没有跑过它**（需要 NVIDIA GPU）
- 它的「18/22 超专家库」是论文数据，我无法在本机验证
- 我们的 3 张卡是**本机实测**的，数字更硬，但样本量小

**如果按「本机可验证的证据」打分，我们的相对位置会好一些。**
但按「系统完整度」打分，差距是真实的。
