## 三、sparse MLA：fp8 版本

四条路径（nosplit / split / tail-split / head-no-split）全部 fp8 化，**正确性全 PASS**
（对反量化后 fp32 参考：max_abs 3.9e-4 ~ 7.8e-3，cosine ≥ 0.9995），576 宽（DeepSeek V4.1）也已验证。

**性能（同进程 ABBA，空载窗口）**：

| 形状 | fp8 | bf16 | flash_mla(bf16) | fp8/bf16 |
|---|---:|---:|---:|---:|
| S=8 topk=2048 | 0.1169 | 0.1375 | 0.5219 | **0.851** |
| S=128 topk=2048 | 1.0667 | 1.2925 | 1.1971 | 0.825 |
| S=8 topk=512 | 0.0796 | 0.0819 | 0.1469 | **0.971** |
| S=128 topk=512 | 0.2908 | 0.3513 | 0.2451 | 0.828（被 fm 反超 19%） |

**结论：fp8 的收益随 topk 走** —— topk=2048 稳定 15~18%；**topk=512（DeepSeek 生产档）只剩 3%**，
因为该档是 overhead-bound，不是带宽受限。

**修掉的一个严重 bug**：fp8 在 topk=512 曾整片出 `inf`。根因是 fp16 partial 缓冲溢出
（fp8 移植后 partial 量纲变成 `448·out/skv`，上界 200704 = fp16 上限的 3 倍，实测 86469）；
topk=2048 当时只用到 53%，是**潜伏 bug**。修法：把 `skv/P_SCALE` 还原提到写 partial 之前（零额外开销）。

## 六、新算子攻坚：MQA logits（进行中）

目标：用 skill 的五步流程做一个新算子，对手是厂商库 **lightop**。

- 模型（`op-roofline/models/mqa_logits.py`）：`AI = 2·q_per_ktile·H/D`，decode 档 `q_per_ktile=1`
  ⇒ AI=64 FLOP/B，远低于平衡点 313 ⇒ **纯访存受限**，杠杆是「把跨 query 的复用并进 GEMM 的 N 维」。
- lightop 基线：m=8 / n=128k / H=32 / D=128 / fp8 ⇒ **0.152~0.162 ms**。
- 我们的 kernel：1.007 ms（6.7× 慢）→ **0.245 ms（1.51× 慢）**，正确性 cos 1.000000。
- **未达标**（目标为超越基线）。剩余差距在 CTA 数与每 CTA 开销（1024 个 CTA，每个只算 8192 FLOP）。

**过程中定位的 3 个静默错误**（都编译通过、不报错）：

1. **3D→2D 拷贝**：`T.copy(Q[m,0,0], q_sh)` 从 `[M,H,D]` 拷进 `[BM*H,D]` 会算错（cos 0.48），必须逐条 2D 拷贝。
2. **MLS 是双边的**：只给 K 挂 `matrix_load` 会算错（cos 0.90）；且目标区域必须静态形状。
3. **串行循环不能访问线程分布维**，必须走 `T.reduce_sum` 或经 shared 中转。
