## 三条演进主线

### 主线 1 · 从「猜」到「测」

- v5.1：分母必须带来源，没有实跑的预测不写
- v6：六组件都配了机器判据
- v7：要求归因到机制（PMC / 指令数 / 字节数），不许说「试了，慢」

### 主线 2 · 从「诊断」到「研发」

- v5.3 起提出「补上改的能力」
- v6 做了 `kernel_scaffold` / `variant_forge` / `forge_step`
- 实测结果：自研 HIP 在 rmsnorm 类算子上超厂商 10.6%、45.1%、103%

### 主线 3 · 从「产出」到「落账」

- v7.2 的标题就是结论：**产出已经超过落账速度**
- 具体表现：成绩是真的，但记分器的输入格式没对上（DS 32 vs 92）
- 这直接催生了「同一事实多处副本」系列的修复

## 被推翻的想法（重点看这个）

| 想法 | 出现于 | 为什么被推翻 |
|---|---|---|
| 从 SkillHub 整体借鉴编排引擎 | v7 | 会造成第三处记账；只该借 `ablate` 与 `branch_explore` 的思路 |
| 用 `min(ms)` 选冠军 | v7 讨论过 | 没有 MAD、没有噪声门，选出的冠军可能是噪声 |
| 固定阈值 `noise_threshold=2%` | v7 讨论过 | 无自适应，本仓已有 `judge()` 四态 |
| 默认从 Triton 起手 | 一直到 v7.2 | 实测：访存受限算子上 HIP 多拿 15~25% |
| `256/VEC2 比 512/VEC1 快 24%` | v6 期间 | 孤立单跑，同批复测只有 1.7% |

**最后那条最值得记**：它是「单点对比分不清两个同时变化的变量」的典型案例，
后来直接催生了 sweep 机制。
