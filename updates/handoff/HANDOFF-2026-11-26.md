## 二、这一夜真正做成的东西

### 1. `scripts/env_probe.py` —— 环境自检（**最重要**）

```bash
python3 -I scripts/env_probe.py --card 4
```

它查四件事：逐卡真跑 kernel / **两种设备绑定方式对照** / 构建产物可信度 / arch 匹配。

**为什么它重要**：昨晚 5 小时的根因，它 30 秒能查出来。

**它的判据踩过一个坑（值得知道）**：第一版只用 `a @ a`（纯 torch）探活，
在 HCU[4] 上报告「两种方式均可」—— 而同一次测试里 `cuda:4` + 自定义 `.so`
明确 dump core。**纯 torch 走 at::native，不受设备绑定 bug 影响。**
现在改成用 ctypes 加载预编译的最小 `.so`，判据才成立。

### 2. `scripts/bench_preflight.py` —— 接进全部 11 个 bench，**默认执行**

```python
# 每个 bench/ab.py 的 main() 里都有这段，默认跑，想跳过必须 --skip-preflight
if not a.skip_preflight:
    from bench_preflight import preflight
    if not preflight(device=getattr(a, "device", None)):
        return 2
```

**「写了个工具」和「接进流程」之间隔了 3 个 bug**（都已修）：
- 查错了卡（无 `--device` 时固定查卡 0，而 `loop.py` 用 env 指定别的卡）
- 探针缓存永不命中（无条件 write 刷新 mtime，每次重编）
- `gpu_guard` 混用物理号/逻辑号（`HIP_VISIBLE_DEVICES=7` 时卡明明空着却判不可用）

### 3. `scripts/minimal_repro.py` —— 递减实验工具

**核心不是跑命令，是顺序。** 标准层序 L1–L6，**「换调用方式」刻意放最后一层。**

**为什么**：D24 那天减到 L5（换成别的算子的 `.so` 也崩）时，我已经证明了
「不是我的代码」，但没证明「不是我的用法」，于是误判成「平台坏了」，多花 40 分钟。

工具在**所有层都崩**时会明确输出：

> 你已经证明了问题不在被测对象。现在该怀疑调用方式。

### 4. 文档：故障 surface 表 + 库边界表

- `Plugins/ops/skills/op-optimize/references/failure-surfaces.yaml` —— **6 条故障定位**
  (`device-bind` / `uninit-struct` / `build-stale` / `verifier-lies` /
  `wrong-variable` / `minimal-repro`)，每条带可跑复现 + D 编号
- `Plugins/ops/skills/op-optimize/references/libraries-bounds.md` —— 库的可用边界

**为什么要单独一页**：这批知识之前只活在 commit message 里，换个人就找不到。

### 5. 判据修复（两个）

- `depth.py` 的 `shape_score` 加**方向判据**：`geomean > 1.0` 时 S=0。
  以前「覆盖 3 个形状」就给满分，不管整体是快还是慢 —— `rmsnorm-fused`
  靠这个漏洞拿过 94 分（实际慢 45%）。
- `scorecard.py` 的 `ledger_rounds` 词表：只认
  `adopt/refute/stalled/采纳/证伪/卡住`。两张 99 分的卡写了 5 轮但用「决定/结论」，
  计数是 0。修完 D4 从 1→3，深度 4.4→4.8。

## 五、踩过的坑（新接手的人会再踩一遍）

### 1. 改文件之前先确认它参与编译

**D17**：我改了一整天 `csrc/api/dense_decode_hip.h`，它是 hipify 生成物
（文件第一行就写着 `automatically generated`），而 `setup.py` 编的是
`api.cpp` → include 的是 `dense_decode.h`。**编译器从来没读过我改的文件。**

**判据**：`grep -r "你的文件" setup.py` 或看入口的 include。
30 秒能确认，我花了一整天。

### 2. 递减实验要减两个方向

减「被测对象」**和** 减「怎么调用它」。
详 `scripts/minimal_repro.py` 的 L6。

### 3. 归因前先控制变量

**`lightop.gemm` 那次**：先测到 K=4096 错、K=256 对，就归因成「K>256 有问题」
并写进卡片。后来控制 M 不变再扫 K，发现 K=256 且 N=4096 时也错 ——
**真正的变量是 M（M≥24 就错）**。

### 4. 「验证器说通过」需要被验证

**D16**：`fmla_patch.py --check` 报「补丁在」，实际 `grep` 是 0 处。
判据是「取 new 里最长的一行代码判断」，而那行**本来就存在于原文件**。

**这不是孤例**：`env_probe` 第一版也是假判据（只测纯 torch）。
新增的每个检查器都要问：**它会不会在应该报错的时候报通过？**

### 5. GPU「使用率 0%」不等于「能用」

- `hy-smi` 显示 0%、显存 140GB 空闲，但 `cuda:N` + 自定义 kernel 会崩
- `gpu_guard` 判「干净」和 `env_probe` 判「能用」是**两件事**
