## 一、这段时间做成了什么

### 1. 三张卡，都有实测证据

| 卡 | 结果 | 口径 | DS |
|---|---|---|---|
| `rmsnorm-fused` | 自研 HIP 比 lightop 快 1.12x | event_isolated | 74 |
| `fused-add-rmsnorm` | 自研 HIP 比 lightop **快 1.82x**，精度更好（0.50 vs 1.50 ULP） | event_isolated | **92** |
| `norm-act-swiglu` | 三合一融合比两步法 **快 2.03x**（流量 369→168 MB） | event_isolated | **89** |

全部 `acc_ok=True` —— 这是全项目第一批可 claim 的记录。
`rmsnorm-fused` 的 74 分偏低，是因为它的接收链路的数字没更新（见 §四）。

### 2. 精度门从「恒 False」到能出结论

**根因不是实现不准，是链路断了**：
- `bench/acc_probe.py` 不存在 → `loop.py` 静默跳过整块精度检查
- `decide()` 拿到 `maxdiff=None` 就提前返回 → 即使补了 acc_probe 也白测
- `acc_probe` 收到的是候选 id 不是变体名 → acc 字典永远匹配不上

三处都修了。现在 `acc_ok` 能正常产出。

**同时把容差从固定 `max_abs` 改成 ULP 判据**：bf16 只有 7 位尾数，
ULP 随量级变（[0.5,1) 2^-8 / [1,2) 2^-7 / [2,4) 2^-6）。四个变体在
`max_abs=2e-3` 下**全 FAIL 含厂商 lightop** —— 判据错，不是实现错。

### 3. 语言选型从「默认 Triton」变成「按场景判」

**两层问题**：
1. `scripts/lang_select.py` 早就能判，但**没有任何代码调用它**
2. 判据是定性描述（「纯 elementwise，Triton 已足够」）—— 没人能执行

改法：`lang-candidates.yaml` 加 `routing.rules`，输入是 roofline 的四个数
（bound / utilization / remaining / launch_fraction），在 `advance.py` 的
`build_plan` **之前**执行。

实测：
```
fused-add-rmsnorm (util=0.831, remaining=0.203) → 先评估手写 HIP
rmsnorm-fused     (util=1.002, remaining=-0.002) → 已接近上限，用 triton 微调
```

### 4. 冷启动：新算子有入口了

`scripts/op_bootstrap.py`：从算子描述生成最小可跑卡（卡 + contract +
SKILL.md + variants.yaml + shapes + _common 骨架），并立刻算 bytes 和 floor。

**必须知道的边界**：新算子流程是 6 步，第 4 步不能省：

```
op_bootstrap → 补 reference → 跑一次基线 → floor → lang_select → advance
```

没有 `t_actual` 时语言路由输出「无规则命中」。不是缺陷——不知道该多快
就不知道该往哪走。

## 二、三个反复踩的坑（都已有机器判据）

### 坑 1 · 分母错 → 结论方向反

这段时间复现了 **6 次**：

| 次 | 错法 | 错值 | 真值 |
|---|---|---|---|
| 1 | 1100 nominal 当分母 | util 低 | 用 achievable |
| 2 | 227.0 已在 ledger 作废，roofline 还在用 | remaining +12.2% | -2.6% |
| 3 | 把 121µs 的带宽安到 140µs 上 | 1664 GB/s | 1438 |
| 4 | `MB/ms × 1000` 当 GB/s | 419576 | 420 |
| 5 | 同上，在 permute 卡再犯 | 同上 | 同上 |
| 6 | 给含归约的实测上限再加归约折扣 | util 118.8% | 96.2% |

**教训**：`MB/ms` 本身就等于 `GB/s`，再乘 1000 就大三个数量级。
`floor.py` 的公式是 `bytes_mb / t_us * 1000`（µs 不是 ms），两个公式长得像。

### 坑 2 · 校验本身没被校验

- `scorecard` 的判据比较「文件名 vs 文件内容」→ 永远 False
- `surfaces.yaml` 11/17 条 `precondition_check` 恒失败（`grep traffic` 查的键不存在）
- `ingest_check` 只查记录内字段，顶层 `absorption` 数组整个漏检
- 同一条规则在 4 个地方各写一份，改一处漏三处

**每条都补了反向测试**（构造该报错的输入，断言它真报错）。

### 坑 3 · 写了不等于接上了

| 工具 | 状态 |

## 五、怎么验证这套东西是好的

**唯一验收：盲测一个新算子。**

```bash
# 1. 建卡
python3 -I scripts/op_bootstrap.py --name <新算子> --family <f> \
  --shape "M=...,H=..." --inputs "..." --outputs "..." --pattern <p>

# 2. 补 reference（不能跳过 —— 它是正确性的唯一锚）
# 3. 跑一次基线，拿到 t_actual
# 4. 出 roofline，看语言路由给什么建议
python3 -I scripts/lang_select.py --card <新算子> --shape s0

# 5. 跑完整循环
python3 -I scripts/advance.py --card Plugins/ops/skills/op-<新算子> --max-rounds 3 --forge
```

**合格线**：出现 `significant=true` + `acc_ok=true` + `measure_mode=event_isolated`
的记录，且卡片 `ratio < 0.95`。

## 六、纪律（这几条是血换来的）

1. **分母必须带来源**。任何峰值常数都要有 `reproduce` 指向真实脚本。
2. **A/B 必须同批**。孤立单跑出来的「快 24%」，同批复测只有 1.7%——
   base 漂移会被算成收益。
3. **校验器必须被校验**。每条规则配一个反向测试（构造该报错的输入）。
4. **写了要接上**。工具存在但没人调用，等于没有。
5. **不要往 schema 加字段**。先跑 `scripts/check_schema_fields.py`。
   同一个错犯过三次（`comparison_note` / `downgrade_reason` / `status='draft'`）。
