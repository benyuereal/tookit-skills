# comm

集合通信（AllReduce / AllGather / ReduceScatter / All2All）。

## 为什么不建算子卡

**这一族不进 op-atlas 的实现层。** 三条理由：

1. **kernel 不属本仓库**。集合通信的 kernel 实现属 RCCL 团队，
   本仓库既改不动也不该改。建卡会让人以为这里有优化空间。
2. **和 op_card 的契约对不上**。算子卡的五件套是
   `contract.yaml` / `variants.yaml` / `shapes.yaml` / `_common.py` / `bench`，
   它们的前提是「有一个可替换的 kernel 实现」。通信没有这个东西。
3. **真正的杠杆在别处**。通信慢的时候，能动的不是 kernel，而是
   **通信与计算的重叠编排**——那是引擎层的决策（并行策略、CP/DP 切分、
   图捕获时机），结论受显存水位与预热策略共同影响，
   **不能写进任何算子卡的 last_verdict**。

## 该归到哪

| 关注点 | 去哪 |
|---|---|
| RCCL 配置、拓扑检查、通道调优 | `dcu-env` 的 `dcu-rccl-test` |
| 通信与计算的重叠编排、并行策略选型 | `docs/ENGINE.md` 的 L1 选型 / L2 闭环 |
| 通信是否已重叠好的判据 | `pipeline.md` 的 **Q6 重叠判据** |
| all2all 与 MoE dispatch 的关系 | MoE 家族的 `moe-dispatch` 条目（若建卡） |

## 本族判据（供重叠分析用，不建卡）

1. **先算两侧耗时比**：compute_floor 与 comm_time 接近（0.5~2 倍）时重叠收益最大；
   一方远大于另一方（>5×）时重叠无意义，先把大的那一侧降下来。
2. **重叠需要额外 buffer**：这会把 smem/显存预算推高，与 Q4 的预算不等式一起算。
3. **"已经重叠好了"的判据**是：实际耗时接近 `max(compute, comm)`，
   而不是接近 `compute + comm`。

## 关于「实现横评」节的豁免

**本族豁免「实现横评」节。** 理由：

横评的前提是「同一层里有两个以上可比的实现」。通信族里不存在这个前提——
kernel 属 RCCL，本仓库没有可替换的实现；而引擎层的并行策略（CP8/DP8 等）
与 kernel 不在同一层，同表比会得出错误结论（这一点已在 MoE 家族的横评里
作为反例写明）。

如果强行写一节横评，内容只能是「RCCL vs RCCL」，或者把引擎层混进来——
前者无意义，后者有害。所以豁免，并把原因留在这里。
