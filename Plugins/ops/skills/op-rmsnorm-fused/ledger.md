## 二、天花板算式（本卡是校准判据的最佳载体）

```
不融合残差：读 x + 读 w + 写 y = 2*M*H*2B
融合残差  ：读 x + 读 r + 读 w + 写 y = 3*M*H*2B

prefill-8k（M=8192, H=4096）不融合：2*8192*4096*2 = 134 MB
内存地板 = 134 MB / 1724 GB/s = 78 µs
```

**字节数完全确定、无中间态、无复用** ⇒ 达成率的分母没有争议。
这是全仓库最适合校准「带宽判据」的算子。

## 三、已确立的事实

| 事实 | 机制 | 影响 |
|---|---|---|
| 融合残差是唯一真收益 | 省一次 HBM 往返（3→2 或 4→3 次） | 不融合残差的变体上限就低一截 |
| `eps` 在 sqrt 内外数值不同 | `sqrt(mean+eps)` vs `sqrt(mean)+eps` | 小值输入下可见 |
| 原地写残差会污染多变体对比 | 后跑的吃到被改的输入 | 每个变体喂独立副本 |
| 用标称 1100 做分母会误判到顶 | 已有空间被算成 87% | 一律用实测 1724 |

## 八、S3 迭代记录：SwiGLU 的 46% 缺口（Case 001 后续）

> 承接 `op-optimize/cases/001-swiglu-fused-vs-split`：那里测得融合版
> 达成率 46%（copy 峰值口径）。这里按场景表往下追两轮。

### 轮 1：vectorize-width（layout-pack）—— **证伪**

**假设**：bf16 下向量化宽度被限制在 8B 而非 16B，导致带宽上不去。

**测法**：固定 M=32768，扫 H ∈ {2048, 4096, 4097, 8192}。
若向量化宽度受限，H 不是 8 的倍数（4097）时应出现明显掉档。

| H | median | 带宽 |
|---|---|---|
| 2048 | 0.7718 ms | 522 GB/s |
| 4096 | 1.5102 ms | 533 GB/s |
| 4097 | 1.5115 ms | 533 GB/s |
| 8192 | 2.9766 ms | 541 GB/s |

**判定**：**证伪**。H=4097（非 8 倍数）与 H=4096 的带宽**完全相同**（533 vs 533）。
若向量化宽度是限制，这里应有可见落差。

```
mechanism: 向量化宽度不是瓶颈。H 从 2048 到 8192、含非 8 倍数，
           带宽稳定在 522-541 GB/s，无掉档。
           判据：同 kernel 换 H 奇偶性，带宽变化 < 2%。
```

### 轮 2：coalesce-check（gather-path）—— **假设不成立，但指向真因**

**假设**：读 `[M, 2H]` 非连续，导致有效带宽只有峰值的三成。

**测法**：同字节数（读 M*2H + 写 M*H）下对比「融合 swiglu」与「纯 copy」。
若访存模式是问题，纯 copy 应该快得多。

| 实现 | median | 带宽 |
|---|---|---|
| 融合 swiglu | 1.5272 ms | 527 GB/s |
| 纯 copy（同字节） | 0.5142 ms | **1566 GB/s** |
| | | **2.97x** |

**判定**：**假设不成立，但结论更有价值**——
访存**没有**结构性缺陷（纯 copy 同字节能到 1566 GB/s，接近 copy 峰值 1125 的
1.4 倍是因为这个 copy 只读一半写一半，实际上限更高）。

```
mechanism: 差距 2.97x 说明瓶颈不在「读 x 的访存模式」，
           而在 kernel 内部：融合 kernel 要从 [M,2H] 的两半分别读
           （gate 半与 up 半）并做跨半的乘，这打断了流式访问。
           纯 copy 是单段线性读写，能跑满带宽；
           swiglu 是「读两块 + 跨块元素乘」，天然不是单流。
           判据：同字节数下 copy 1566 GB/s vs swiglu 527 GB/s。
next:      下一轮该试「改变数据布局让 gate/up 分块连续」
           （即把 [M,2H] 拆成两个 [M,H] 独立张量喂入），
           而不是继续调 kernel 参数。
```

### 轮 3：layout-split（layout-pack）—— **证伪轮 2 的推论**

**假设**（来自轮 2 的推论）：把输入从单个 `[M, 2H]` 拆成两个连续的 `[M, H]`
张量，消除 gate 半与 up 半的跨块访问，应该能提升带宽。

**测法**：同 M=32768 H=4096，对比「单张量喂入」与「拆成两个后 cat 回去喂入」。

| 布局 | median | 相对 |
|---|---|---|
| 单张量 `[M, 2H]` | 1.5298 ms | 1.00x |
| 拆成两 `[M, H]` 再 cat | 2.2808 ms | **1.49x（更慢）** |

**判定**：**证伪**。拆布局在当前 API 下不成立——`FuseBiasSwiGLU` 的接口
要求 2H 宽的连续输入，拆开之后必须 `torch.cat` 拼回去，而 cat 本身
就是一次完整的 HBM 往返（读 2 份写 1 份），代价远大于它省下的访问不连续。

```
mechanism: 「数据布局」这条路的成本被 cat 吃掉了。FuseBiasSwiGLU 的签名
           绑定 [M,2H] 连续输入，任何「先拆开」的方案都要在调用前拼回去。
           cat 的字节数 = 读 2*M*H + 写 2*M*H，与 swiglu 本身同量级，
           所以净效果是负的（实测 1.49x）。
           判据：拆后 2.2808 ms vs 单张量 1.5298 ms。
next:      要么改 FuseBiasSwiGLU 的接口接两个张量（需改库源码，属 source-patch），
           要么接受当前布局——46%/39% 的达成率是这个接口形态的固有成本，
           不是实现缺陷。这一轮的结论把问题从「布局」推到了「接口」。
```

**对轮 2 结论的修正**：轮 2 说「下一轮该改数据布局」，轮 3 证明
在**不改库接口**的前提下那条路走不通。真相是：瓶颈是**接口形态**
（要求 2H 连续输入 + 内部跨半访问），不是数据摆放。

### 三轮小结

| 轮 | 方向 | 判定 | 机制 |
|---|---|---|---|
| 1 | vectorize-width | **证伪** | 带宽与 H 奇偶无关（533 vs 533） |
| 2 | coalesce-check | **假设不成立，指向真因** | 同字节 copy 1566 vs swiglu 527，差 2.97x，瓶颈在跨半元素乘的访存不连续 |

**这两轮的价值**：把一个含糊的「46% 还有空间」变成了具体的
「空间在数据布局，不在 kernel 参数」。下一轮该改布局，不是调参。


## 2026-11-23 二次修正：等语义下我们**慢 6.7%**，此前的「快 1.18x」作废

### 我们少写了一份输出

`lightop.fused_add_rms_norm(x, residual, w, eps)` 返回**两个**张量：
  `out ≈ rmsnorm(x+r)*w`，`residual_out ≈ x+r`（实测 maxerr 0.0156）
且 **x 与 residual 都被原地改写**。

我们的 `fused-3pass-triton` 最初只 `store(Y)`，**没有把 x+r 写回**。
→ 流量 201 MB，比 lightop 的 268 MB 少 25%。**少干 1/3 的活，然后说自己快。**

### 等语义口径（都写 2 份输出 = 2读2写 = 268.4 MB）

M=8192 H=4096 bf16，64 buffer 轮换，40 次中位，event 隔离：

| 实现 | 时间 | MAD | 带宽 | util(1724) |
|---|---|---|---|---|
| `fused-3pass-triton`（补 residual_out 后） | 242.2 µs | 1.4 µs | 1108 GB/s | 0.643 |
| `lightop.fused_add_rms_norm` | 227.0 µs | 5.0 µs | 1182 GB/s | 0.686 |

**等语义下我们慢 6.7%**（业主独立测得 11.9%，同量级，差异来自时钟档位）。

### 但融合本身是值的（换成正确的对比对象）

  add 134 µs + rms_norm 143 µs = 277 µs（分离方案）
  → 融合 242.2 µs = **1.14x**

**这才是「融合残差 RMSNorm」的价值。此前拿融合版比单算子，是比错了对象。**

### 一条必须记住的口径纪律

**跨实现比较前必须先对齐 (inputs, outputs)。** 不对齐就是在比两件不同的活。
卡片新增 `inputs` / `outputs` / `traffic_passes` 三个字段，validate 用 E27 守。

### 关于 lightop 的那个假报错

`_common.py` 曾写「变体在本机不可用：需先安装 lightop 的融合 norm 实现」——
**这是假的**：lightop 0.6.0 早已安装（203 个顶层符号可用）。
这句谎话让 ledger 里「待验证：lightop-fused 的实际达成率」挂了很多轮没人发现。
已改为「adapter 尚未实现（注意：lightop 实际已安装）」。

### 未测定

- 补 warp 级归约后能否追平（next_probe 已指向这条，目标 ≥1360）

## 2026-11-23 三种实现的分布：瓶颈是访存模式，不是 DSL

### 等语义口径（2 读 2 写 = 268.4 MB，prefill-8k）

同进程交替多轮、events 隔离、6 组 buffer 轮换：

| 实现 | 中位 | 带宽 | 相对 add 上限(1634) |
|---|---|---|---|
| lightop `fused_add_rms_norm` | 195.4~197.4 µs | 1360~1374 GB/s | 84.1% |
| tilelang（blk_m=1, threads=256） | 199.5~213.0 µs | 1260~1345 GB/s | 82.3% |
| triton（num_warps=1~4） | 211.2~221.0 µs | 1214~1271 GB/s | 77.8% |
| — 纯 elementwise add（无归约，参照上限） | 123.2~125.4 µs | 1634 GB/s | 100% |

（两次独立测量的区间；排序在两次间有 ±1 名的波动，但三者全部落在 1200~1380 这个带内。）

### 结论（这条是给后面 45 张卡用的）

**三种实现全落在 1200~1380 GB/s，离纯 copy 可达 1749~1801 还有 22~39%。**

这条分布说明：**瓶颈是「2 读 2 写交织 + 行内归约」这个访存模式本身，不是某个框架写得差。**
换 DSL（triton → tilelang）最多给你 3~10%；要拿 25% 以上，只有两条路：

1. **in-place**：residual 写回输入的 r 本身，省 write-allocate
2. **融进下游**：不落 HBM，268 MB → 201 MB → 134 MB

### 一条被推翻的旧结论

此前记的「行内归约天花板 = streaming × 0.75」**是错的**。
0.75 不是硬件规律，是**当时那个 triton kernel 的 codegen 上限**。
实测 tilelang 与 lightop 都能到 0.82~0.84。

⇒ 以后写「这是上限/地板/结构性限制」，必须配一句：
**「我用什么方法证的，换哪种实现能推翻它」。** 说不出来就别写。


## 2026-11-23：write-allocate 实验 —— in-place 路线证伪（5 分钟省下一天）

in-place 的理论收益是「省掉 write-allocate 的额外读」。**先测这个前提是否存在。**

2GB 张量、event 隔离、20 次中位：

| 模式 | 时间 | 带宽 |
|---|---|---|
| 纯写 `fill_` | 2.050 ms | 1048 GB/s |
| 1:1 `copy_` | 3.636 ms | 1181 GB/s（按 2×字节合成） |

**copy 的合成带宽 1181 > 纯写 1048**（比值 1.13）。

若有 write-allocate，写之前要先读一遍旧数据 ⇒ copy 的有效带宽应**低于**纯写。
实测反而更高 ⇒ **DCU 的写路径没有 write-allocate**。

### 结论

**in-place（residual 写回 r）在本机是零收益。** 不要投入。

这条也解释了为什么 lightop 的原地改写版（207 µs）与我们 out-of-place 的 tilelang 版（212 µs）
只差 2%——省掉的不是 write-allocate，只是分配开销。

### 剩下唯一能拿 25% 的路

**下游融合**：268 MB → 201 MB → 134 MB。这是唯一量级够大的方向。
