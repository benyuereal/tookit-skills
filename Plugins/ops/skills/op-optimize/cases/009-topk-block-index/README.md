# Case 009：top-k block 选择 —— 达成率判据不适用，该用「离 launch 地板多远」

> 起点：`topk-block-index` 卡 status=draft。
> **本 case 的产物是「判据要换」这件事本身**，不只是几个数。

## 0. 为什么前几个 case 的判据在这里是错的

前四个 case（rope / MLA / GEMM）都是 bandwidth 或 compute 受限，用「达成率 of peak」判。
这个算子不是：

```
L=8192, K=2048, B=32 时输入只有 1.6 MB
→ 1724 GB/s 下 1.6 MB 只要 0.93 µs
→ 而一次 kernel launch 就要 43 µs
```

**数据量比 launch 开销小 46 倍。** 在这种量级下算「带宽达成率」没有意义——
分母（峰值带宽）在这儿根本约束不到任何东西。

判据改成 **耗时 ÷ 空 kernel 耗时**：
- ≈1 ⇒ 已经在下限，任何优化都没意义
- ≫1 ⇒ 有真实工作量，值得看

## 1. 轮 0：launch 地板

```
空 kernel（out.add_(1)）：43.2 µs
```

这是本 case 的「分母」。注意这个数本身就很大——它不是 kernel 在算，
是 DCU 的 launch 固定开销。

## 2. 轮 1：硬前提 —— page_table 必须 2D 且 stride(1)==1

| 输入 | 结果 |
|---|---|
| 1D page_table | 拒绝：`Expected src_page_table.dim() == 2 && src_page_table.stride(1) == 1` |
| 2D contiguous | OK，out=(8, 2048) int32 |

这是调用方最容易踩的坑：**语义上 page_table 就是一维映射，
但接口要求 2D（每序列一行）且行内连续。**

## 3. 轮 2：扫 B / L —— 耗时几乎不变

| B | L | median | MAD | 输入 MB | vs launch |
|---|---|---|---|---|---|
| 1 | 8192 | 0.0440 ms | 0.0011 | 0.03 | 1.02× |
| 8 | 8192 | 0.0334 ms | 0.0006 | 0.39 | **0.77×** |
| 32 | 8192 | 0.0342 ms | 0.0006 | 1.57 | **0.79×** |
| 8 | 32768 | 0.0458 ms | 0.0005 | 1.18 | 1.06× |

**B 放大 32 倍（输入放大 46 倍），耗时只从 0.0334 涨到 0.0342 ms（+2%）。**

甚至出现了 <1 的比值（0.77×）——那不是超光速，是两次测量踩在不同的
launch 路径上（空 kernel 那次 43.2 µs 偏高）。**但方向是明确的：
这个 kernel 的耗时基本就是 launch 开销。**

## 4. 轮 3：vs `torch.topk` —— 专用 kernel 值 5×

| B | L | lightop | torch.topk | 快 | 显著 |
|---|---|---|---|---|---|
| 8 | 8192 | 0.0342 ms | 0.1749 ms | 5.11× | 是 |
| 32 | 8192 | 0.0350 ms | 0.1790 ms | 5.11× | 是 |
| 8 | 32768 | 0.0461 ms | 0.1405 ms | 3.05× | 是 |

三档全部显著（|Δ| > 3×MAD）。**这是本卡 primary 选 lightop 的直接依据**——
不是「文档说它好」，是同语义下 3~5× 的耗时比。

## 5. 结论

```
① 判据：本算子该看「离 launch 地板多远」，不是「带宽/算力达成率」
        数据量比 launch 开销小 1~2 个数量级，带宽分母在这儿不构成约束
② 实测 0.77~1.06× launch ⇒ **已经没有可优化的空间**
③ 专用 kernel 比 torch.topk 快 3.05~5.11×（三档全部显著）⇒ primary 选它是对的
④ 硬前提：page_table 必须 2D 且 stride(1)==1
```

### 对卡的含义

**这张卡应该标「已到地板」而不是继续找优化点。**
在它上面花时间不会有回报——它的耗时已经是 launch 的代价。

这也给了一个通用判据：**先量 launch 地板，再决定要不要优化。**
本 case 的 43 µs 是这个仓库里第一个明确的 launch 基线。

## 7. 一条可迁移的经验

「融合能省多少」在本机有个天然上限：**每次 launch ~43 µs**。
如果某个流程里有 N 个串行小 kernel，理论上限就是 N×43 µs。
这条数（43 µs）之前没有记录过，现在有了。
