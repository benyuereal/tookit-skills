# Case 002：MoE pipeline 段级拆解（MegaMoE 式融合的可行性排查）

> 前面 001 是单算子级（一个 kernel、一个场景、一个 ratio）。
> 这一例是 **pipeline 级**：MoE 的收益不是把某个 GEMM 写快，
> 而是把五段收进一个持久化算子、消掉中间落盘。
>
> **所以先要的不是优化，是段占比。** 没有它，后面全是猜。

## 阶段 0：五段分段计时

```bash
python3 stage_timing.py --M 4096    # P 档（大 M，compute-bound）
python3 stage_timing.py --M 32      # D 档（小 M，latency-bound）
```

口径：**CUDA event，不是 time.time**（异步 kernel 用 time.time 会被量成 0）；
每段之间 `synchronize`，不含前后段；每段单独 warmup；报 median + MAD。

### P 档（M=4096, H=2048, I=1408, E=32, K=4）

| 段 | median_ms | MAD | 占比 |
|---|---|---|---|
| gate_up_gemm | 7.0837 | 0.0045 | **47.8%** |
| down_gemm | 6.1352 | 0.0022 | **41.4%** |
| combine | 1.0074 | 0.0003 | 6.8% |
| swiglu | 0.3891 | 0.0010 | 2.6% |
| dispatch | 0.2190 | 0.0120 | 1.5% |
| **合计** | **14.8344** | | 100% |

### D 档（M=32）

| 段 | median_ms | MAD | 占比 |
|---|---|---|---|
| gate_up_gemm | 5.4931 | 0.0118 | **48.0%** |
| down_gemm | 5.4867 | 0.0069 | **47.9%** |
| combine | 0.2187 | 0.0040 | 1.9% |
| dispatch | 0.1717 | 0.0010 | 1.5% |
| swiglu | 0.0784 | 0.0026 | 0.7% |
| **合计** | **11.4486** | | 100% |

## 阶段 0 的结论（会影响后面所有阶段的假设）

**两个 GEMM 占了绝对大头，而且小 M 时占比更高：**

| 档 | 两个 GEMM 合计 | 三段非 GEMM（dispatch+swiglu+combine） |
|---|---|---|
| P（M=4096） | **89.2%** | 10.9% |
| D（M=32） | **95.9%** | 4.1% |

**这推翻了「先做融合消落盘」的默认假设。**

「把五次下发收进一个算子、消掉四趟中间落盘」这个思路，收益上限是
**非 GEMM 的那 4-11%**——因为它只能省 dispatch / swiglu / combine 之间的
中间态，动不了两个 GEMM 本身。

也就是说：
- 如果两个 GEMM 的实现已经接近地板，**融合最多省 4-11%，且要付融合的复杂度**
- 如果两个 GEMM 离地板很远，**先优化 GEMM 比先融合划算得多**

**下一步必须先回答**：这两个 GEMM 各自离各自的地板有多远？
在回答之前，做融合是在优化那 4-11%，而不是那 89-96%。

## 一个必须说明的口径限制

这里的五段是**用 torch 逐专家循环搭的未融合基线**，不是任何生产实现。
它的用途是**拿占比**，不是拿倍数——逐专家循环本身比真正的 grouped GEMM 慢，
所以「两个 GEMM 占 89-96%」这个结论在真实实现里会被稀释。

**但它稀释的方向是确定的**：真实实现里 GEMM 更快，
所以非 GEMM 段的占比会**上升**。这意味着融合的上限比 4-11% 高一些，
但不会高到「融合优先于 GEMM 优化」的程度。

后续阶段要换成真实 grouped GEMM 重测，才能给出准数。
**在那之前，任何「融合能省 X%」的说法都是未测定的。**

## 未测定项（不插值、不假装）

## 阶段 1：段级选型（两个 GEMM 的地板与达成率）

```bash
python3 stage1_gemm.py    # 见 results/stage1-gemm.json
```

### grouped vs 逐专家循环

形状 E=32, M/exp=128, N=1536, K=2048, bf16：

| 实现 | median | MAD | TFLOPS |
|---|---|---|---|
| `deepgemm.m_grouped_bf16_gemm_nt_masked`（mode 1000） | 0.3205 ms | 0.0149 | **80.4** |
| 逐专家 `torch.mm` 循环 | 1.0171 ms | 0.0149 | 25.3 |
| | | | **3.17x，|Δ|=0.697 > 3×MAD=0.045，显著** |

### 达成率：26%（远未到顶）

```
bytes = 230.7 MB，grouped 带宽 720 GB/s
算力地板（bf16 实测峰值 310 TF）= 0.0833 ms
达成率 = 0.0833 / 0.3205 = 26%
```

> ⚠️ 2026-11-23 更正：原写「43%，分母 185 TF」。那个 185 是由 19.7 条 MFMA/cyc
> 反推的，实测同机 hipBLASLt 大 GEMM 能到 310 TF（N=6144）。**实测值高于声称的峰值，
> 说明常数错。** 分母从 185 换成 310，达成率从 43% 降到 26%——
> 结论方向不变（都远未到顶），但「还有多少空间」从 2.3× 变成 3.8×。
> 复跑：`op-roofline/tools/calibrate_bf16_peak.py`。

**这更正了阶段 0 的推论。** 阶段 0 用的是逐专家循环（25.3 TFLOPS），
它让两个 GEMM 看起来占了 89-96%。真实 grouped 实现快 3.17x，
所以**非 GEMM 段的真实占比会比阶段 0 高**——但 GEMM 本身 26% 的达成率
说明它也远没到顶。

**净结论**：现在既不能断言「融合优先」，也不能断言「GEMM 优先」。
两个方向都还有空间，需要阶段 2 的拐点来定。

### 实测到的硬约束（L2 选型必须记）

| 约束 | 现象 |
|---|---|
| masked 形态要求 **N 被 256 整除** | 真实 MoE 的 I=1408 被直接拒绝 |
| `a` 必须 **3D `[E, M, K]`**，`b` 必须 **3D `[E, N, K]`** | 传 2D 会 IndexError |
| `mode=1000` 是 asm layout，`pack_bf16_masked_weight` 只做 contiguous | — |
| `mode=2000` 需真 pack | — |

### ll 路径拐点：**未测定**（诚实标注）

`m_grouped_fp8_gemm_nt_masked_ll` 要求 `b` 是 **6D packed layout**
（报错：`expect tensor matrix_b is 6 which is 3`），而 deepgemm
**没有公开的 6D pack 函数**。

试过的路径：
- 2D/3D + `pack_bf16_masked_weight` → matrix_b 维度不够
- fp8 tuple `(tensor, scale)` 输入 → 同样维度不够

**这正是 MegaMoE 的 pack5 权重布局缺口在 DCU 上的对应物。**
按纪律标为「未测定」，**不插值、不假装测过**。

> 「ll 路径在多少 token 以下才用」这个问题，在当前可见的 API 下**无法回答**。
> 要回答它得先有 6D pack 实现——那是阶段 5 失败模式库里该记的一条。

## 阶段 2：融合 vs 拆分的交叉点 M* —— **未测定，但试过三个入口**

```bash
python3 stage2_crossover.py    # 见 results/stage2-crossover.json
```

### 分段路径：7 个 M 点全部可测

| M/exp | 分段 median |
|---|---|
| 8 | 0.2659 ms |
| 16 | 0.2685 ms |
| 32 | 0.2712 ms |
| 64 | 0.2898 ms |
| 128 | 0.3229 ms |
| 256 | 0.3907 ms |
| 512 | 0.7082 ms |

M/exp 从 8 涨到 512，耗时涨 **2.66x**——斜率明显，说明分段路径的固定开销
在小 M 时被摊薄得不够。

### 融合侧：三个候选全部不可用

| 候选 | 结果 | 判定 |
|---|---|---|
| `aiter.asm_fmoe_stage1` | **有完整可用的 schema**（`out, input, gate, down, sorted_token_ids, sorted_weights, sorted_expert_ids, num_valid_ids, top_k, scale_a, scale_b, …`），但两种 dtype 都被拒：`BFloat16 → unsupport current input type`；`float8_e4m3fn → 同样报错` | **此卡（gfx938）上 asm 后端不可用** |
| `aiter.asm_fmoe_stage2` | 同一组 asm 后端 | 跟随不可用 |
| `lightop.fuse_groupgemm_permute_quant` | 存在，但只融合 permute+quant 两段 | 不是五段合一，不能当融合侧对照 |

> `asm_fmoe_stage1` 的 schema 是完整的——这说明**接口设计上它就是要做
> 五段融合的**（gate/down 两段 GEMM + 激活，一次调用）。问题不在接口，
> 在于当前的 gfx938 构建不支持它需要的 dtype。asm 源码不在包里
> （预编译 .so），无法进一步确认它到底支持什么。

### 结论

**M* 未测定，且不是「没试」而是「融合侧没有能跑的入口」。**

要测 M*，必须先满足其一：
1. asm 后端在 gfx938 上按需要的 dtype 编出来
2. 另找一个 fp8 grouped-fused-MoE 实现

在满足之前，**任何「M<M* 拆分、M>M* 融合」的说法都是编的**。

这条应进阶段 5 的失败模式库（class: hard —— 不是性能问题，
是路径根本不存在）。

## 阶段 3：重叠验证 —— 判别法与被证伪的假设

```bash
python3 stage3_overlap.py
```

### 判别法（不靠总时间下降）

```
重叠度 = (串行和 - 并行) / min(t_A, t_B)
```
分母用 **min** 而不是 `(串行和 - max)`：物理上「最多能隐藏多少」就是较小那一侧的全部耗时。

### 三种情形实测

| 情形 | 单独 A / B | 串行 | 并行 | 重叠度 |
|---|---|---|---|---|
| `copy_`(D2D) + GEMM | 3.4 / 3.7 ms | 7.10 | 6.69 | **11.9%** |
| GEMM + GEMM | 3.6 / 3.6 ms | 7.32 | 7.11 | **5.8%** |
| **D2H(pinned) + GEMM** | 18.2 / 3.7 ms | 21.76 | 18.04 | **100.0%** |

### 结论：只有真 DMA 引擎才能重叠，D2D copy 不能

反直觉但实测坐实：
- `copy_`（D2D）看着像访存，实际和 GEMM **抢同一个引擎**，叠不起来（11.9%）
- 两个 GEMM 必然争用（5.8%）
- **D2H 到 pinned 内存**才走独立 DMA 引擎，能把 3.7 ms 的 GEMM **完全隐藏**（100%）

### 一个必须先修的方法缺陷（这一轮最重要的教训）

第一版用 1GB copy（1.6 ms）配 8192 GEMM（27.5 ms）。copy 只占 **5.9%**，
窗口 1.6 ms 被 27.5 ms 的噪声淹没——**同一台机器两次跑出 92% 与 0%，结论完全相反**。

修法：两侧耗时调到同一量级（3.4 vs 3.7 ms）。
**报重叠度时必须同时给两侧耗时比**，否则读者无法判断结论是否可信。

### 对 MoE 的意义

两段 GEMM 同属算力引擎，**分流无法重叠**（实测 5.8%）。
「把两段 GEMM 放两个流并发」这个想法**在本平台是错的**。
真能重叠的只有「计算 vs 真 DMA」——对应 HiCache KV 备份、权重预取这类 D2H/H2D。

## 阶段 2b：融合三级阶梯 —— 可执行的 M*

阶段 2 的二元对比做不出结论（全融合侧不可用）。改成三级阶梯：

| 级 | 内容 | 状态 |
|---|---|---|
| **L0** 全拆分 | 手工 permute → deepgemm grouped → swiglu | 可跑 |
| **L1** 部分融合 | `lightop.fuse_groupgemm_permute_quant`（融 topk+permute+quant） | **可跑** |
| **L2** 全融合 | `asm_fmoe_a8` | **不可用**（failure-modes 第 1 条 hard） |

### 拐点实测

| M/exp | L0 全拆分 | L1 部分融合 | L1/L0 | 谁快 |
|---|---|---|---|---|
| 16 | 0.3427 | **0.2014** | 0.59x | L1 |
| 32 | 0.3376 | **0.2782** | 0.82x | L1 |
| 64 | **0.3661** | 0.4534 | 1.24x | L0 |
| 128 | **0.4088** | 0.8342 | 2.04x | L0 |
| 256 | **0.4504** | 1.6758 | 3.72x | L0 |

**交叉点在 M/exp ∈ [32, 64]。**

```
M/exp < 32   ⇒ 用 L1 部分融合
M/exp > 64   ⇒ 用 L0 全拆分
M/exp ≈ 32-64 ⇒ 实测决定（两者接近）
```

### 为什么这个 M* 才有用

「能不能一步到位用全融合」答不了（L2 不可用）。
但「从哪一级开始换」是可以执行的决策——给定 token 数就能选 L0 还是 L1。

**机制**：L1 的收益来自省掉 permute 与 quant 的中间落盘；这部分开销在小 M 时
占比高、在大 M 时被 GEMM 摊薄。所以小 M 融得值，大 M 不如直接跑 GEMM。

## 阶段 4：共享专家并行 —— 结论是「做了也没用」

MegaMoE 自己承认这是短板：共享专家在融合核外，要等路由专家算完才启动。
所以测「挪到独立 stream 并发」是否真能赚。

```bash
python3 stage4_shared.py
```

| 组合 | 串行 | 双流并行 | 重叠度 |
|---|---|---|---|
| **shared(GEMM) + routed(GEMM)** | 0.450 ms | 0.467 ms | **0.0%** |
| D2H(真 DMA) + routed(GEMM) —— 对照组 | 1.502 ms | 1.074 ms | **100.0%** |

### 结论：同引擎，并发不成立

- shared 与 routed **都是 GEMM，同属算力引擎** → 双流只是把两个 kernel
  排到同一队列的不同流，硬件仍串行发射 → **0.0%**
- 对照组 D2H 走独立 DMA 引擎 → **100.0%**

**这个反差本身是最硬的证据**：不是测量方法有问题（对照组满分），
是引擎类型的问题。

### 对 MegaMoE 的意义

「把共享专家挪到独立 stream」这条路**在 DCU 上不成立**——不是「没做」，
是「做了也没用」。要缩短共享专家的等待，只能从**减少它的绝对耗时**入手，
不是并发。

### 又一次踩到同一个坑（值得记）

对照组第一版用 512MB D2H（17.4 ms）配 routed（0.31 ms），
窗口只占 **1.8%**，测出 18.4%——那是噪声。
把 D2H 缩到与 routed 可比（1.175 ms）后立刻回到 100%。

**这是阶段 3 记录过的同一个缺陷，我又犯了一次。**
说明「窗口纪律」不能只写在文档里，得写进脚本的断言。
