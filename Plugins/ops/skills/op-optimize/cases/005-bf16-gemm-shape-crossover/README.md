# Case 005：bf16 GEMM 的 M 拐点 —— 同一张卡，小 M 与大 M 是两个算子

> 起点：`gemm-bf16` 卡 status=draft。它是所有量化档的基准，
> 但「基准」只有在说清**它在哪个形状受什么约束**之后才成立。

## 0. 先定判据，再测

不靠肉眼看 TFLOPS 跳动定性。用两个地板：

```
内存地板 = (M·K + N·K + M·N)·2B / 1724 GB/s
算力地板 = 2·M·N·K / 310 TF          ← 本机实测峰值，不是标称
```

实测时间更接近哪个地板，就是哪个约束。两个地板都同进程重测，
避免跨进程漂移。

> ⚠️ 2026-11-23 更正：本 case 第一版分母写 310 TF，是**单轮采样的偶发高值**。
> 10 轮独立采样的峰值中位数是 **279 TF**（详见 `op-roofline/tools/calibrate_bf16_peak.py`）。
> 另外「峰值」与「稳态」是两个口径：本 case 表里是 median（稳态），
> 与峰值分母混用会把达成率低估约 16%。卡的 last_verdict 已改用 peak 口径。

## 1. 轮 1/2：扫 M，K=N=4096

| M | ms | TFLOPS | of peak | GB/s | 内存地板 | 算力地板 | 约束 |
|---|---|---|---|---|---|---|---|
| 1 | 0.0680 | 0.5 | 0.00 | 494 | 0.0215 | 0.0001 | memory |
| 16 | 0.0658 | 8.2 | 0.03 | 514 | 0.0216 | 0.0017 | memory |
| 32 | 0.0662 | 16.2 | 0.05 | 514 | 0.0218 | 0.0035 | memory |
| 64 | 0.0709 | 30.3 | 0.10 | 488 | 0.0221 | 0.0069 | memory |
| 128 | 0.0854 | 50.3 | 0.16 | 417 | 0.0228 | 0.0139 | memory |
| **256** | 0.0989 | 86.9 | 0.28 | 382 | 0.0241 | **0.0278** | **compute** |
| 512 | 0.1531 | 112.2 | 0.36 | 274 | 0.0268 | 0.0555 | compute |
| 1024 | 0.1632 | 210.5 | 0.68 | 308 | 0.0322 | 0.1111 | compute |
| 2048 | 0.2859 | 240.3 | 0.78 | 235 | 0.0429 | 0.2222 | compute |
| 4096 | 0.5275 | 260.5 | 0.84 | 191 | 0.0644 | 0.4444 | compute |

**拐点 M ≈ 256。** 判据是两条地板在哪一档交叉（M=128 时内存地板 > 算力地板，
M=256 时反过来）。这不是选的数字，是算出来的。

### 两个观察

1. **小 M 的带宽只有 494~514 GB/s（峰值的 0.29~0.30），不是 1724。**
   M=1~32 时理论上只要读 B（16 MB）+ 写 out，是纯读。实际只到 0.3，
   说明小 M 下 GEMM kernel 的读模式不合并——它按 tile 读 B，tile 内沿 K 方向
   是连续的，但**跨 tile 的 B 行跨度**让有效带宽掉到 0.3。
2. **M=512 有一个凹陷**（112 TF，比 M=256 的 86.9 高但没到 M=1024 的 210）。
   这是 kernel 选择切换的区间，不是稳定工作点。**M=512 附近别下结论。**

## 2. 轮 3：换 N=14336（SwiGLU 的 up+gate 宽度）

| M | ms | TFLOPS | of peak | GB/s | 约束 |
|---|---|---|---|---|---|
| 32 | 0.1336 | 28.1 | 0.09 | 888 | memory |
| 128 | 0.1608 | 93.5 | 0.30 | 760 | memory |
| **512** | 0.2834 | 212.2 | 0.69 | 481 | compute |
| 2048 | 0.8923 | 269.5 | 0.87 | 216 | compute |

**拐点从 M≈256 移到 M≈512 之间。** 因为 N 变宽后，每行的算力密度上升，
分母里算力那一项涨得更快。⇒ **拐点不是常数，是形状的函数**，
卡里不能写「M>256 就是算力受限」这种固定阈值。

## 3. 轮 4：同一形状换路径 —— F.linear 比 torch.mm 慢 8%

| 路径 | M=1024 | M=2048 | M=4096 | M=4096,N=14336 |
|---|---|---|---|---|
| `F.linear(a, b[N,K])` | 0.1594 | 0.2819 | 0.5216 | 1.7278 |
| `torch.mm(a, b.t())` | 0.1434 | 0.2570 | 0.4800 | 1.6514 |
| 比值 | 0.900 | 0.911 | 0.920 | 0.956 |

**稳定慢 8~10%，四个形状一致，MAD 都 <0.005。**

这不是布局转换开销：profiler 显示两边跑的是**同一个 kernel**
（`Cijk_Alik_Bljk_BBH_MT256x256x16_SE_AMAS3_BW_DTL0_BL1_DRB16_A`），
只是耗时不同（516.4 µs vs 483.6 µs）。说明 F.linear 的 dispatch 在 bf16 上
选到了同一 kernel 的次优 launch 参数。

`a @ b.t()` 与 `torch.mm` 结果一致（0.4803 vs 0.4800），
⇒ 差异来自 `linear` 这一层，不是 `.t()` 的 transpose。

**这条直接进 L2 选型**：常规稠密 GEMM 优先用 `torch.mm` / `@`，不用 `F.linear`。

## 4. 结论

```
① 拐点由两条地板交叉点决定，随 N 移动：K=N=4096 时 M≈256；N=14336 时 M≈512
② 小 M（<128）达成率只有 0.00~0.16，且带宽只到 0.30 ⇒ 受访存模式限制，不是算力
③ 大 M（>=2048）达成率 0.78~0.87 ⇒ 基本到顶，没有大空间
④ F.linear 比 torch.mm 稳定慢 8~10%（同 kernel，dispatch 选参差异）
```

### 对优化方向的含义

| 档位 | 有空间吗 | 往哪切 |
|---|---|---|
| decode 小 M | **有**（0.30 带宽 → 理论上能接近 1724） | 改读模式（合并访问 / 按 tile 重排），不是调 tile 大小 |
| prefill 大 M | **没有**（0.84~0.87） | 别在这上面花时间 |

## 6. 对本卡（`gemm-bf16`）的落点

- `ratio` = 0.84（M=4096，K=N=4096 档），vs 写「本机实测 bf16 峰值 310 TF」
- `best_for`：M≥2048 的 prefill GEMM（0.78~0.87）
- `not_for`：decode 小 M（0.00~0.16，且带宽只有峰值的 0.30，另一个问题）
- `modify_path` 改成「换调用形式」：`torch.mm(a, b.t())` 而非 `F.linear`，实测 8~10%
