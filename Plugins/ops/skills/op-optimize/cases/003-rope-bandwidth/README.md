# Case 003：rope 的带宽只有峰值两成 —— 追根因

> 起点：`rope` 卡实测 360 GB/s，流式峰值 1728，达成率 **0.21**。
> 场景归属 `bandwidth-bound`，按场景表取攻击面。

## 0. 按场景表选攻击面

```bash
python3 loop.py -C <卡> enumerate --scenario bandwidth-bound
```

```
1  fusion-boundary  这一档唯一的真收益是省 HBM 往返
2  layout-pack      每多一次布局转换就多一趟读写
3  gather-path      非合并访问到不了流式峰值
已知死路：✗ 优化计算部分（这段没在等算力）
```

`fusion-boundary` 对本例**不适用**——rope 已经是单 kernel，没有链可融。
直接走第 2 项 `layout-pack`。

## 1. 三轮探测（`bench.py`，全部可复跑）

### 轮 1：放大规模 —— 排除「固定开销主导」

| S | median | GB/s |
|---|---|---|
| 512 | 0.2304 | 291 |
| 2048 | 0.7728 | 347 |
| 8192 | 3.0488 | **352** |

S 放大 16 倍，带宽只从 291 涨到 352 就平了。
**⇒ 不是固定开销，是访存本身的问题。**

### 轮 2：同字节纯 copy —— 上限参照

| | median | GB/s |
|---|---|---|
| rope（S=8192） | 3.0488 | 352 |
| 纯 copy 同字节 | 0.8445 | **1271** |

**3.6 倍差距。** 拷贝能到 1271，说明内存系统没问题，问题在 rope 的访问方式。

### 轮 3：扫 D —— 找真正的机制

| D | median | GB/s | vs D=128 |
|---|---|---|---|
| 64 | 2.8342 | 189 | 0.55x |
| 128 | 3.1051 | 346 | 1.00x |
| 256 | 3.8314 | **561** | 1.62x |

**带宽随 D 单调上升，近似线性。**

## 2. 结论

```
根因：每线程连续处理的字节太少（向量宽度不足）
证据：① 带宽与 D 近似线性（189 → 346 → 561）
      ② 都远低于同字节 copy（1271）
      ③ 不是固定开销（S 放大不改善）
      ④ 不是 freqs 开销（实测占主字节 0.008）
```

**即使 D=256 也只有 561 GB/s（峰值的 0.32）**，说明还有另一半空间。

## 3. 为什么不下「已到顶」

达成率 0.21 对逐元素算子是偏低的。同类的 `mlp-swiglu`（case 001）
达成率是 0.39-0.46，`rmsnorm-fused` 在 M=8192 时是 0.51。
rope 只有 0.21，说明它的访问模式比这几个都差。

## 4. 要突破需要什么（未做）

| 手段 | 代价 |
|---|---|
| 改 kernel 让每线程处理更多连续字节（相邻 head 合并成一次向量读） | 需手写 HIP 或改 aiter 源码 |
| 换 rotate_style 的实现 | 两种 style 差 0.02ms，不够 |

**本 case 只做到「定位根因」，没做到「修好」**——改 kernel 属 source-patch，
需要走 op-source-patch 的六步，不在本轮范围。
