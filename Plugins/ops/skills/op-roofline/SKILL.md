# 机器模型：先算，再写

## 一、为什么需要它

`op-optimize` 解决「跑完别骗自己」，解决不了「想不出来」——它只对现有 kernel 做局部变形，产不出不存在的东西，也解释不了为什么。本项目 27 条实现级判死里，**至少 6 条编译前就能算掉**（`merge`/`kv4`/`g2s`/`bm64`/`thr128`/`bi64`）——那不是实验结果，是没有模型时的学费。**有预测，才是在优化；没预测，是在赌博。**
预测 0.69 ms、实测 0.69 ms ⇒ 你懂了。预测 0.40 ms、实测 1.20 ms ⇒ **模型错了，回去修模型**，不是再换一个变体试。第三种（没有预测，试完记一笔「这个不行」）才是我们一直在干的。

## 二、三层结构

```
constants.yaml（物理常数，实测标定，带 provenance/status）→ rules/（推导规则：可计算、带反例、带校准点）
→ models/<op>.py（算子模型：shape + 设计 → 预测耗时 + 绑定约束）→ 实测（只做一件事：给模型打分，残差 = 模型健康度）
```

**绑定约束**是输出的核心。不是「预测 0.69 ms」，而是「**预测 0.69 ms，绑定约束 = 非 MMA 指令发射**，内存侧还有 3× 富余」；只有后者能告诉你下一个改动往哪走。

## 三、判据

1. **写不出预测说明还没理解它为什么慢** —— 这是回去补模型层的信号，不是直接开始写代码的信号。
2. **一个数只能有一个分母。** 报「达峰 87%」时同时给峰值来源（标称 vs 实测）；换分母能把「到顶了」变成「还有 1.8×」——本项目真发生过（见 `constants.yaml:conflicts`）。
3. **规则要能被证伪。** 每条写成「若 X 则 Y」，附一个**会推翻它**的观测；不能证伪的不是规则，是描述。
4. **相对量可信，绝对量可疑。** 「多花 76 VGPR」通常对；「总共 342 VGPR」只在活集合意义上对（临时量不进声明段）。

## 四、现有规则（每条都能算，且都交过学费；设备相关结论为 gfx938 实测，换设备要重测）

| 规则 | 算式 / 判据 | 状态 |
|---|---|---|
| **R1 寄存器活集合** | 活变量声明量 ≥ 每线程上限（gfx938 768-VGPR 模式 256；其他 gfx 未验证）⇒ **保证溢出**，编译前即可否掉 | 已校准 |
| **R2 双 GEMM 布局正交** | 两次 GEMM 的收缩维正交（QK 收缩 `d`、PV 收缩 `k`）⇒ 一个 fragment 无法同时满足两侧的 8-连续要求 ⇒ **必有一侧付标量 LDS**，与写法无关 | 可证明 |
| **R3 在途缓冲需要切换对象** | 每 CU 只驻 1 个 CTA 时，预取/深流水只会增加寄存器压力，不会隐藏延迟 | 已校准 |
| **R4 访问粒度决定有效带宽** | 有效带宽 = f(每线程连续字节数)；16 B 可达实测流式峰值的 94~97%，4 B 面远低于此 | 部分校准 |
| **R5 小工作量不是效率上限** | 总字节小到跑不进稳态时，实测 GB/s 反映的是占用率与平底，**不能当该访问模式的效率上限** | 已推翻一条旧结论 |
| **R6 LDS 预算** | 单 CTA 的 shared 需求 > 64 KB×85%（gfx938 实测）⇒ 「块数减少省固定开销」这类预测**作废**：编译器会把 buffer 挤进 VGPR/scratch，并发与向量化同时崩 | 已校准（修正了一次 −18.6% 的错判） |
| **R7 更快的数据通路先查编译期前置条件** | 某条通路/指令报「前置条件不满足」时，先查它写死的编译期约束（dtype / kPack / arch），**不要先怀疑调用方式**。例：MLS 要求 `kPack=1`，bf16 因 gather 向量化宽度必须 `kpack=2` ⇒ bf16 用不了 MLS，换写法也没用 | 已校准（编译期直接拒，见 `references/rules.md` R7） |

细则、反例、校准数据见 `references/rules.md`。工具：`tools/hipbudget.py`（R1 的可执行版，**作用域感知**：兄弟块/分支取 max，不把不同作用域的声明平铺求和）、`tools/probe_peak.py`（从 rocminfo / hy-smi 反推 CU/wave/HBM/峰值，与 `constants.yaml` 逐项对账，偏差 > 2% 报警）。

## 五、怎么用

```bash
python3 derive.py sparse-mla --s 128 --h 64 --topk 2048 --nvalid 2000 --bm 32 --thr 256      # ① 出预测与绑定约束（不用卡、不用编译）
python3 derive.py sparse-mla ... --measured-ms 0.7799                                         # ② 有实测后对账：残差 > 30% 回去修模型
python3 tools/hipbudget.py path/to/generated.hip --live acc_o,Q_spilt,KV_spilt --threads 256   # ③ R1：会不会溢出
python3 tools/probe_peak.py --check                                                           # ④ 常数是否漂了
python3 scripts/probe_stream.py --check                                                       # ⑤ 流式峰值实测（read/copy/write 三口径）
python3 scripts/probe_pattern.py --runs 128 256 512 linear                                    # ⑥ 访问模式自己的 ceiling
```

④ 校验的是**手抄常数**；⑤ 是**当场实测**的流式峰值（`constants.yaml` 的 `stream_*_peak` 分母就是它），
两者对不上时以实测为准并改 constants。⑥ 给的是「行内连续 X 字节」这类 kernel 的物理上限：
**用线性峰值给它算达成率，分母就错了**（R4 的可执行版）。

`derive.py` 的输出有且只有一个目的：**指出绑定约束**——下面同时给出三件事：当前分子多少、可达上界多少、下一刀该切哪。

`hipbudget.py` 输出只有两种有意义的结论：**判为溢出**（活集合峰值 ≥ 单线程上限）⇒ 这个设计大概率到此为止；**未超限** ⇒ 不保证不溢出（临时量不进声明段，实测可多出 ~148 VGPR），下一步才是编译 + 读 `vgpr_spill_count`。两者都**不是绝对数值判定**：活集合按「同作用域相加、兄弟块/分支取 max」估算，绝对量必须以编译产物 `vgpr_count / vgpr_spill_count` 为准；可靠的是**两个设计之间的相对比较**。

### 对账的另一半在 `op-profiling`

本 skill 是**预测侧**（shape + 设计 → 上界 + 绑定约束，不需要卡）；预测对不对要靠硬件计数器对账——那套口径（TA_* 跨 SE 求和、L1 无命中率计数器、首次 launch 虚高、CU 数每卡不同）全在 **`op-profiling`**，这里不重复。两者对不上：**残差大就回去找漏掉的物理约束，不是换变体再试一次**（见 §六）。

## 六、模型健康度

模型的价值等于它的**残差**。每次实测都要记：预测 vs 实测（残差 > 30% 要写清是哪一层错了：常数 / 规则 / 算子模型）；绑定约束对不对（预测「卡在指令发射」而 PMC 显示卡在内存 ⇒ 模型结构性错误，比数值误差严重得多）；外推距离（只有两个校准点时，中间的插值别当真）。**别用「调参把残差压小」的方式修模型**——那是在拟合噪声；残差大就回去找漏掉的那条物理约束。

## 七、与其他 skill 的关系
`op-contract`：模型给出**地板**，契约 `floor` 应引用模型预测而非标称值。`op-bench`：提供测量口径，模型与测量互为闭环。`op-profiling`：对账的另一半。`op-optimize`：预测变成候选队列的 `expect`，`expect` 是候选进队列的判据。`op-gate`：判定门，模型预测用于判「这个数字合理吗」。

## 七·五、流水线演算（写主循环之前）

写任何 gather/GEMM 主循环之前，先按 [`references/pipeline.md`](references/pipeline.md) 答四问：
**消费者数**（能不能 global→VGPR 直喂）→ **在途单位**（放 VGPR 还是 LDS）→ **气泡宽度**（要几个 buffer）→ **预算不等式**（可行性）。

**四问答不出来，说明模型层还没补齐。** 本项目有三次实验（预取 1/2/3 片、bm64）如果先算，一次都不用做。

## 八、落点

- 本 skill 只放**物理常数**（实测标定，可复核）与**推导规则**；具体形状的绝对 ms 预测结论进 `~/.config/dcu-toolkit/kb/op-opt/`。
- 常数带 `source` + `verified_on` + `status`（measured / derived / unverified）；两个来源冲突时**并列记录**，不取平均、不挑好看的那个。
