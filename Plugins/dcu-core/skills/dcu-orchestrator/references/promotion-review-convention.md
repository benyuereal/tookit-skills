# 沉淀审批块约定（promotion-review-convention）

> 用途：任何一次任务/处理结束后，如果收集到了「可跨项目复用」的事实，都按本文约定把**收集结果呈现到会话**，由人工决定是否合入 skills。
> 适用范围：op-distill（算子优化沉淀）、fault-triage（故障处理经验）、deploy-verify（部署核对）、research-baseline（调研复现）等一切会产出可复用事实的任务；不止 op-distill。
> 本文是「工作流 + 内容纪律」，属于本包内容；**git 提交/推送等发布动作不进本文**，由各使用环境自身的纪律处理（见文末「发布边界」）。

## 一、何时用

- 任务执行中产生了**值得沉淀的领域事实**（手法 / 坑 / 架构约束 / 结论），且该事实**可能被后续其他项目复用**。
- 用户没有显式说"这次不沉淀"。

## 二、收集什么

只收集满足下面门槛的事实，一条条列出，**每条都带三个属性**：

| 属性 | 取值 | 说明 |
|---|---|---|
| `scope` | `<gfx代际>` / `<卡型>` / `跨机型` | 该事实在什么硬件上成立 |
| `status` | `verified` / `unverified` | 是否已实测验证；未验证一律 `unverified`，不得写成结论腔 |
| `依据` | `<证据路径>` / `<run 产物>` / `<profiling>` | 事实从哪来，可回查 |

**不收集**（明确排除，别沉淀成 skill 内容）：
- 环境专属结论（绑定某设备/某版本/某镜像）；
- 一次性参数（某次 shape / 并发 / 绑核 / 卡位）；
- 未验证的猜测（status=unverified 只能作候选，不进 skill 正文）；
- 纯性能数字（标 `[历史数据]`，只留台账与项目留痕，不进事实库）。

> 数字纪律：任何写进台账/候选的数字必须能回到 run 产物字段或命名的证据；**不推断、不补全、不美化**（缺字段标 `MISSING`）。

## 三、呈现审批块（发到会话，不写死）

沉淀结尾，把收集结果以标准**审批块**发到会话（不是只写盘），让用户拍板：

```
【本次沉淀待审批】
可复用事实（候选）：
- <一句话事实> | scope=<gfx代际/卡型> | status=verified|unverified | 依据=<证据路径>

拟并入：<目标 skill 文件路径>（如 dcu-kernelwiki/wiki/<topic>.md）
明确不并入：<环境专属 / 一次性参数 / 未验证 / 纯性能数字>

请选择：
① 合入             —— 把批准且已脱敏的事实写进拟并入的 skill 文件
② 只留台账         —— 只留着本机知识库台账，不改任何 skill
③ 修改后再合入     —— 你告诉我怎么改，我改完再合入
④ 放弃本次沉淀     —— 只留本次任务产物，不写台账也不改 skill
```

- 审批块里的每个候选事实，都必须**已经过脱敏**（见下节），不能让使用者的本地实测值冒出来。
- 纯咨询/只读类任务（没有可复用事实）**不带**审批块。

## 四、合入前脱敏闸（护共享包，必做）

本包是可被他人 clone 的 vendor 包；**合入任何事实前必须先脱敏**，否则使用者的本地实测值（设备号/IP/容器名/真实用户名/内网仓库/工单号）会漏进对外包。按 skill-package-hygiene 硬排除处理：

| 敏感项 | 处理 |
|---|---|
| 裸设备号 / 机型 / 卡数 | 语义化：`跨NUMA机型` / `单NUMA机型` / `多机型`，或用公开占位 `<device-A>`；不写真实编号 |
| 真实 IP / 主机名 | 占位 `<device_ip>` / `<device_host>` |
| 容器名 / 业务用户名 / 个人标识 | 占位 `<container>` / `<user>`（如 `<container>…`、`<internal-user>-…` 都要脱） |
| 内网仓库 / 内网 registry URL | 占位 `<internal_registry>/<image>:<tag>`（包自身发布 URL 除外） |
| 明文密码 / token / 凭证 | 绝不进包；只放 git-ignored 外部配置，文档从环境变量读（`SSHPASS` / `sshpass -f`），不内联 |
| 内部模型变体名 | 用公开名 `qwen3-32b` / `qwen3-series` 等，或占位；别用杜撰的伪型号 |
| file_id / 工单号 | 占位 `<internal-file-id>` / `<internal-ticket>`；或写「内部文档，不对外」 |

> 脱敏口诀：**保留可复用的手法/坑/约束，占位掉具体设备/IP/人/仓库/版本变体**。判断某条该不该进：它是不是"换个环境照样成立"的事实？是→保留（配 scope/status）；否→归"明确不并入"。

## 五、合入动作（人工选 ① / ③ 后）

1. 把"拟并入"中**已通过脱敏**的候选事实，逐条落到目标 skill 文件（追加到对应章节，或按该 skill 已有结构放）。
2. **保留 scope 与 status**：每条注明适用硬件范围与验证状态；`unverified` 的只作候选提示，不进 skill 正文结论。
3. **不并入项**绝不写进 skill（环境专属 / 一次性参数 / 未验证 / 纯数字）。
4. 遵守目标 skill 自身的结构/命名/语言习惯（与兄弟 skill 标题语言一致，别插入英文样式 outlier）。
5. 改完后，按包的 Hygiene 自查跑一遍同类脱敏 grep。

## 六、发布边界（重要）

- 本文**不规定**是否 `git push`、推哪个分支、是否造 PR——那是**各使用环境自己的治理/执行纪律**，不属于包内容。
- 典型区分（供执行者判断，不是包内硬规则）：
  - **作者 / 权威主库本机**（有推送权限，且用户明确授权可按仓库纪律提交）：`git add` 只加自己改的文件 → commit → 推对应分支。
  - **普通使用者 / 克隆包**：只落本地改动（或生成 patch / 说明），**不自动推远端 master**；改不改、推哪由使用者决定。涉及对外发布还要另过对外适宜性审查。
- 一句话：**包只定义"收集什么、怎么呈现、合入哪些、脱敏到什么程度"；"推不推、推哪"留给环境自己的纪律。**
